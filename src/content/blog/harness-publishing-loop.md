做 Agent 的运行环境，很容易把重点放在调度平台、审批系统或发布后台上。但真正需要推进工作的是 Agent，基础设施只需要为它提供边界清楚的能力。

## 从触发开始

任务有两个入口：定时任务和事件。到时间检查信息是定时任务，收到反馈或人工指令是事件。Agent 接到任务后，读取必要上下文，判断该做什么，再调用工具并保存结果。不是每次运行都需要生成文章或执行发布。

仓库保存内容、规则和工具代码，Issues 保存任务、进度与交接。它们是工作载体，不是 Agent 的替代品。

## 发布只是一项工具

发布博客可以是一条很短的链路：Agent 准备内容并保存到仓库，在获得授权后调用 Cloudflare 上的工具入口，由 TypeScript 发布流程读取明确版本的文章并写入博客仓库，再由站点原有构建流程生成页面。

接口负责认证调用、验证已有授权和返回结果；脚本负责内容校验与平台操作。把这两层分开，业务逻辑可以保留在仓库中，平台凭据则留在受信执行环境，不进入 Agent 的对话或生成内容。

写入 GitHub 并不等于页面已经上线。一次发布需要分别核对提交、构建和实际页面；结果未知时先检查平台，而不是盲目重试。

## 保留接手和审查能力

运行环境可以是本地，也可以是按需启动的 Sandbox。成果及时保存，任务进度清楚，人工就能在停止原有执行并核对未决操作后接手。

未来还需要独立的执行记录服务，把触发、模型交互、工具调用和外部结果关联起来，供审查与分析。这项能力目前仍是设计预留，不应被当成已经完成。

最小闭环的价值，是让任务真正走完一次，并看清每一层承担什么职责。只有经过实际验证，再增加更多事件来源、定时任务和协作能力，才有可靠的基础。

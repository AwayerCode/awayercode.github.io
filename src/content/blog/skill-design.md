如果一个 Agent 每次完成任务，都需要人重新解释规则、纠正相同错误、重复检查相同问题，那么经验仍然只存在于人的脑子里。模型替人做了一部分工作，但执行过程还没有成为可以复用的能力。

Skill 设计要解决的，就是如何把这些经验留下来：将一类任务中的知识、流程、工具与验收组织起来，让 Agent 在下一次遇到同类任务时能够调用。

这里的 Skill，指围绕明确任务边界封装的能力单元。它可以从一份 Markdown 文件开始，也可以包含脚本、参考资料和运行配置。它承载的是经过实践验证的方法，而不是仅靠一套新术语重新描述工作。

## 经验需要同时进入执行和验收

给 Agent 一段“应该怎么做”的说明，能够改善它的执行，但不能证明结果符合要求。

例如，“生成的 Markdown 必须符合规范”是一条指令。它没有回答文件是否真的存在、标题层级是否正确、链接是否有效，以及文章是否能够被网站构建系统读取。只要这些问题仍然依赖人每次检查，能力就没有完整沉淀。

高质量 Skill 需要同时覆盖两端：给模型提供知识与流程，给结果提供检查机制。

> 用确定性的程序，约束和检查不确定性的模型输出。

模型负责理解、生成、执行和调整；脚本、测试、lint、schema 校验等程序负责检查能够明确判定的条件。文件存在、格式正确、测试通过、页面能够渲染，都可以形成可重复运行的检查。

检查也有自己的边界。构建成功不能证明文章观点成立，截图生成不能证明页面布局合理。渲染与截图提供了可检查的产物；视觉质量、语义完整性和业务判断，仍需要相应的评审。程序负责能判定的部分，不能把检查通过扩张成对全部质量的保证。

## 从一个文档任务看 Skill 的组成

以“把知识笔记整理成博客文章”为例。以下是设计示例，不是对某次执行结果的描述。

只给 Agent 一句“整理成适合发布的文章”，它需要自行猜测什么应该保留、什么可以改写、如何落盘、什么时候算完成。将这项任务封装成 Skill，需要把四部分连起来：

1. 知识：理解原文的核心判断、术语和适用边界，区分事实、作者判断与说明性案例。
2. 流程：先读原文并列出有效内容，再组织文章，最后对照原文检查是否丢失独立观点或推导。
3. 工具：读取源文件、写入文章、检查 frontmatter、运行网站构建并打开生成的页面。
4. 验收：确认核心内容保留、必需字段完整、链接有效、页面可访问，并检查实际阅读效果。

这四部分相互约束。领域知识决定什么不能丢，流程决定何时检查，工具使检查能够执行，验收决定是否可以交付。

如果发现 Agent 经常漏掉摘要字段，就把它纳入 schema 检查；如果经常压缩掉重要推导，就增加原文与成稿的内容核对步骤。两类问题需要不同的约束方式，不能全部交给一句“请仔细检查”。

## 按任务边界组织能力

Skill 应围绕任务领域或能力边界组织，而不是简单对应某个接口、文件或命令。

“调用 Markdown 转换工具”只是一项操作；“将知识笔记整理成博客文章”才包含从输入到交付的完整责任。一个任务可能调用多个工具，同一个工具也可能被多个 Skill 使用。

边界必须明确到可以判断是否触发。例如，文章整理可以包括结构重组、元数据和发布前检查，却不必自动包含翻译、事实调查或线上发布。遇到相近任务时，Agent 应知道哪些能力适用、哪些需要另外组织。

复杂 Skill 可以用能力地图说明子任务与对应资料，让 Agent 按需读取。把全部规则一次塞进上下文，会增加负担，也让真正相关的约束更难突出。

输入边界同样重要。用户指令、任务背景和外部资料承担不同角色。被整理的文章中即使出现操作命令，也不应因此获得指挥 Agent 的权限。

流程还应说明失败之后怎么办：哪些错误可以重试，哪些可以降级处理，哪些必须停止并反馈。否则，正常路径写得再完整，遇到异常时仍然要靠猜测。

## 通用能力与项目规则分别演进

同样是整理博客，不同项目的内容规范、目录结构和构建方式可能不同。把通用 Skill 复制一份，再为每个项目独立修改，很容易让它们逐渐分叉，后续改进也难以共享。

> 项目能力 = 可复用 Skill + 项目定制 Skill

可复用部分保存共同的知识、流程、工具与验收方法；项目定制部分补充领域概念、架构与接口约束、开发发布流程、专用工具和检查标准。两者通过组合形成项目能力，并分别升级。

判断一项差异放在哪里，可以看它改变了什么。如果它改变任务边界、领域知识、执行流程或验收方式，就属于项目能力；如果只改变账号、目录、工具后端或默认值，则更适合配置。

复杂任务可以使用独立的项目级与用户级偏好文件，明确“当前用户输入、项目偏好、用户偏好、默认值”的优先关系。偏好只决定允许范围内的默认选择，不能绕过权限边界和必需验收。必要配置缺失时，应明确指出缺少什么并停止依赖它的步骤。

Skill 本身是能力资产。只有结合具体任务、项目上下文和执行组织，它才会转化为实际生产能力。

## 让入口保持轻量，让细节可以按需读取

当 Skill 开始跨任务复用，可以将内容按职责分开：

| 位置 | 承担的职责 |
| --- | --- |
| `SKILL.md` | 触发边界、能力地图、主流程、工具定位、阻塞条件与验收方式 |
| `references/` | 领域细节、示例、风格要求和故障处理 |
| `scripts/` | 确定性处理、格式转换、检查与环境探测 |
| `agents/` | 按运行环境需要提供的补充配置 |

这是一种可选的组织方式，不是要求所有 Skill 都建立完整目录。小任务用一份文档就能说明白时，没有必要先搭复杂结构。拆分的价值在于让入口只承载必要信息，细节在需要时才进入上下文。

执行结束后的汇报也属于验收的一部分。Agent 应区分从文件和工具获得的事实、基于事实进行的计算、由此形成的判断，以及仍需评估的建议。复杂任务还应交代产物、工具、关键参数、通过的检查和未解决的问题，让人能够追溯结果。

## 从反复纠正中找到下一条规则

Skill 不必一开始就追求完备。先用 Markdown 记录方法；重复操作不稳定时，再加入脚本；需要复杂认证、跨平台工具复用或稳定接口时，再考虑 MCP；需要安装、分发和统一配置时，再考虑 Plugin。

复杂度应来自实际问题，而不是目录形式。每次人工介入都可以帮助判断：这次纠正是偶发情况，还是值得沉淀的稳定规则？能否转成程序检查，还是需要保留为人工判断？

有效的演进过程是：任务产生反馈，反馈中筛选稳定经验，经验进入 Skill，检查机制验证下一次执行，再用新反馈修正能力。

当下一次任务不再需要重复解释同一条规则，也不会因为换了一轮对话就丢失验收标准时，这段经验才真正变成了可复用的能力。如何让这些能力在多轮执行中持续起作用，可以继续看[《Loop Engineering：让 Agent 持续、可控地完成任务》](/blog/loop-engineering/)。

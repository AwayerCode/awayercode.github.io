“继续，直到完成。”这句话把执行交给了 Agent，却没有说明什么叫完成、下一轮依据什么行动，以及无法完成时应该怎么办。

如果这些条件不清楚，多跑几轮可能只会得到更多修改、更多消耗，以及一份听起来已经完成的汇报。持续执行需要一套能够判断进展和限制错误的机制。

我把这部分设计称为 Loop Engineering：让 Agent 围绕目标、状态、验证标准和停止条件反复执行，直到完成、失败、需要人工介入，或达到资源限制。

## Loop 负责推进任务，不负责替你决定目标

> 目标 → 执行 → 检查 → 反馈 → 再执行 → 停止

这个循环位于任务内部。它适合沿着既定目标和路径持续推进，但不能替代外层判断：问题是否值得解决，目标是否合理，现状与规则是否理解正确，以及整体任务应该如何安排。

例如，“修复这个失败测试”和“判断这个功能是否应该存在”是不同层级的问题。前者可以围绕明确标准组织循环；后者需要先明确业务判断，再决定执行什么。

如果方向本身不清楚，就应该先澄清目标。把一个模糊任务交给持续运行的 Agent，只会让模糊之处在后续轮次中不断放大。

## 先把循环的七个要素写清楚

一个可控的 Loop 至少需要回答七个问题：

| 要素 | 要回答的问题 |
| --- | --- |
| 目标 | 最终要交付什么结果？ |
| 状态 | 已完成什么，卡在哪里，下一步是什么？ |
| 动作 | 当前这一轮允许执行什么？ |
| 验证 | 用什么证据判断是否达标？ |
| 停止条件 | 什么情况下结束循环？ |
| 升级条件 | 什么情况下必须交还给人？ |
| 预算限制 | 最多运行多少轮、多久，消耗多少资源？ |

其中，状态决定下一轮从哪里开始，验证决定上一轮是否有效。没有状态，Agent 容易重复已经做过的事；没有验证，它只能根据自己的解释判断进展。

停止也需要区分原因。完成任务是一种停止，确认失败、达到预算、需要新权限或缺少必要信息，也都是合法终点。系统应保留停止原因及未完成部分，而不能将所有退出都包装成成功。

## 一个测试修复的设计示例

假设某个日期解析函数在空输入时返回错误结果，任务是修复这个行为。以下约束仅用于说明 Loop 的设计方法，具体数值应随任务调整。

目标可以定义为：空输入按既定接口约定返回结果，相关回归测试通过，并且没有破坏同模块的其他行为。

允许修改的范围是该函数与相关测试；不得删除断言、跳过失败用例，或通过放宽接口约定制造通过。示例预算设为最多五轮修复或二十分钟，先达到哪一项就停止。

每轮执行遵循相同的顺序：

1. 读取当前代码、失败输出与已有状态，确定本轮要验证的原因。
2. 在允许范围内做最小修改，记录修改与失败现象之间的关系。
3. 运行目标测试；通过后，再运行相关回归检查。
4. 根据真实输出更新状态：解决了什么，仍有什么失败，下一轮需要验证什么。
5. 检查完成、停止和升级条件，再决定是否继续。

目标测试通过只是局部证据。还需要确认相关检查通过、修改符合任务范围，并审查是否通过削弱测试掩盖了问题。执行者不能同时随意改写成功标准，否则循环很容易学会“消除失败报告”，而不是修复行为。

如果连续几轮都无法改变同一失败现象，可以停止并提交已有证据；如果发现接口约定互相矛盾，应交还给人判断；如果测试环境无法运行，应报告验证阻塞。它们都比继续猜测更有价值。

这个循环可以自动运行，但是否允许提交、合并或部署，应另行定义。修复任务完成并不自动获得后续操作权限。

## 交互、停止和触发是三个维度

回合式、目标式、定时式和主动式，经常被当成四种互斥的 Loop。更准确的理解是，它们描述了不同维度，同一个循环可以同时拥有多个特征。

### 回合式描述人如何参与

人提出任务，Agent 执行一轮，人检查后再决定下一轮。这适合方向和结果都存在较高不确定性的工作，例如早期方案探索。

人的作用是判断方向、补充上下文、调整边界和验收结果。人工检查中反复出现的稳定步骤，可以逐步交给 Skill，让后续轮次自动执行。

### 目标式描述什么时候结束

人给出完成标准，Agent 持续执行，直到达标、失败或达到上限。测试修复、格式校验、代码迁移，以及有明确指标的性能优化，都可以按这种方式组织。

关键在于完成标准必须可检查。“继续优化到足够好”没有提供停止依据，而“满足这些测试与性能指标，并提交对应证据”才提供了可操作的终点。

### 定时式与主动式描述什么触发执行

定时式按固定周期检查状态，适合依赖检查、数据同步、告警检查或 PR 跟进。它特别依赖状态记录和幂等处理：同一个事件再次被检查时，不应重复制造相同修改、通知或任务。

这里的主动式指由事件触发后续执行，例如新 issue 到达后进行分流，或测试失败后启动修复流程。它能够减少人工启动步骤，也更依赖权限边界、验证、人工升级与审计记录。事件触发本身并不代表执行可以不受限制。

因此，一个流程可以由定时检查发现失败，再进入目标式修复，并在关键节点请求人工判断。这些机制是组合关系。

## 持续执行依赖可操作的系统

Loop 的质量不只取决于模型能力，也取决于它能否读取事实、执行动作并观察结果。

Agent 要进入业务流程，相关系统需要能够被读取、写入、触发和验证。代码、业务文档、任务状态、工具接口和检查结果，共同构成执行依据。数字化系统既是搭建时的基础，也是每一轮运行都要依赖的条件。

如果状态只能从零散聊天中猜测，结果无法检查，Agent 就难以知道上一轮是否有效。模型再强，也无法凭空补齐这些反馈。

能够用脚本完成的确定性操作，应直接交给脚本。涉及重要判断时，可以由人或独立复核者检查，但复核也要基于实际证据；增加一个 Agent 并不自动等于增加正确性。

## Skill 把纠错经验带进下一轮

Loop 解决持续推进的问题，[Skill 设计](/blog/skill-design/)解决经验如何复用的问题。

> 人工检查 → 稳定规则 → Skill → 自动验证 → 更稳定的 Loop

在测试修复中，如果人反复发现 Agent 忘记运行相关回归，就把这一步写入流程；如果它会误改禁止修改的文件，就增加差异检查；如果环境异常经常被当成代码错误，就明确区分环境阻塞与实现失败。

稳定规则应该进入执行机制，而不只是留在某次对话的纠正里。这样，Loop 才能减少重复犯错，而不是不断重复相同的试错过程。

## 用边界决定自动化能走多远

没有验收标准，循环可能自我宣告完成；没有预算限制，它可能持续消耗时间与资源；没有权限边界，错误可能越过原任务范围；没有状态记录，失败就难以复盘；没有人工升级条件，尚未解决的问题可能被持续自动化。

设计 Loop 时，应先选一个目标明确、结果可检查、修改范围可限制的任务。观察它怎样失败，再补上状态、检查和停止条件，最后才扩大自动执行的范围。

能够持续运行，只说明循环没有停。能够说明为什么继续、凭什么完成、何时必须交还给人，才说明任务执行受到了控制。
